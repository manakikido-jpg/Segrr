# Phase 0 タスク分解(改訂版・2トラック構成)

要件定義書v1.0 セクション3のPhase 0スコープを、実行できる単位に分解したもの。
工数目安: S=半日程度 / M=1〜2日 / L=3日以上(1人開発・AI支援込みの体感値)

**最初の一歩: タスク1から着手する。**

## 改訂の背景

前版はタスク1〜10が完全に直線依存になっていたが、実際には「基盤系(認証・UI・PDF)」と「業務系(顧客→案件→見積→契約→請求)」は別々に進められる。Claude Codeの複数セッション/サブエージェントを使うなら、この2トラックを並行させることで手待ち時間を減らせる。

## 依存関係図(概念)

```
A1 ─┬─ A2 ── B1 ── B2 ── B3 ── B4 ── B5 ── B6 ──┐
    │                          ↑  ↑             ├─ C1 ── C2 ── C3
    ├─ A3 ─────────────────────┘  │             │
    └─ A4 ────────────────────────┘             │
       (C1 は A3 も参照) ───────────────────────┘
```

- B2 は B1 と A3 に依存する(表を正とする)。
- B4 は B3・A3・A4 に依存する。

Claude Codeで進める場合、A1完了後にA2/A3/A4を並行セッションで進め、A2完了を待ってB系を直線的に進める、という形が最も待ち時間が少ない。

## 備考

- タスクB4〜B6が最も工数がかかる(L)。ここが要件定義書セクション5「想定される失敗パターン」の1・3・9・12・13・14に該当するリスクの中心。着手前に必ずセクション5と `docs/db-constraints.sql` を見直すこと。
- **金額・消費税・源泉徴収の合計はすべてDBトリガーが算出する。** サービス層からこれらのカラムを書き込まないこと(対象カラムは `prisma/schema.prisma` 冒頭のコメント参照)。TS側の計算式はUIプレビュー専用で、DBの算出結果と一致することを `tests/unit` で固定する。
- **A2の完了条件はトリガーの実DB検証を含む。** ユニットテストのモックでは検証できないため、ローカルのPostgreSQLに対して実際にINSERT/UPDATEを流して確認すること。ここを飛ばすと三重防御が機能しているつもりで穴が空く。
- タスクB1(認証・Organization)を後回しにしたくなるが、要件定義書で「MVPの段階から権限管理を前提にする」と確定したため、ここを飛ばしてB2以降に進まないこと。
- C1(案件詳細画面)のレイアウトは、この会話中に作成したワイヤーフレーム(タイムライン形式・書類ごとに次アクションボタン)を実装の参考にすること。
