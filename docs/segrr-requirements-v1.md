## 1. 範囲・狙い・合否基準(要件ブリーフ)

### (1) 範囲

**誰のため**
個人事業主・フリーランス・小規模事業者。初期利用者は本人+テスター1人(ドッグフーディング)。**将来的に他人に使わせる/販売する想定が確定** → MVPの段階からマルチユーザー・権限管理を前提にした設計にする(詳細はセクション2・4)。

**解決したい課題**
仕事の書類(契約書・見積書・請求書)と、それに付随する管理業務(進捗・顧客・タスク・経理まわり)がバラバラに管理されていて、一元化されていない。

**主要機能(前回の会話から整理)**

| 大分類 | 内容 |
|---|---|
| 契約書 | 契約書の管理・作成、計画書・覚書の作成 |
| 計画書(契約書の子) | 受注表、タスク管理表 |
| 見積書 | 見積書の管理・作成 |
| 請求書 | 請求書の管理・作成、領収書、確定申告、事業用口座管理 |
| 横断機能 | 進捗管理、顧客管理(CRM) |
| プラットフォーム機能 | 機能の追加拡張、ダッシュボード/表示のカスタマイズ |

これは合計で7〜8個の独立した機能ドメインです。**最終スコープには全部含めるが、同時着手はしない**(確定)。着手順序はセクション3のPhase分割案通り。

**Phase 3まで後回しにする領域(最終的には作るが優先度は最後)**
- 確定申告の自動計算・電子申告連携(税制対応の法令調査が必要。Phase 0〜2では「データを溜める」までにとどめ、必要ならfreee/MoneyForward等へのエクスポートで暫定対応)
- 事業用口座の自動連携(銀行API/アグリゲーションサービスとの契約が必要。それまでは手入力 or CSVインポート)
- プラグイン機構(サードパーティが機能を追加できる本格的な拡張API)
- モバイルネイティブアプリ(それまではレスポンシブWeb → 必要ならPWA化)

### (2) 狙い

契約〜見積〜請求という一連の書類作成・管理を1つのツールに集約し、書類間のデータの継承(見積の項目→契約→請求)を自動化することで、転記作業と管理の分散をなくす。

### (3) 合否基準(案・要確認)

MVPの合格ライン:
- ✅ 見積書を作成→そこから契約書を作成→そこから請求書を作成、という一連の流れがデータの再入力なしにできる
- ✅ 顧客ごとに書類・進捗が紐づいて見られる
- ✅ スマホのブラウザから閲覧・簡単な入力ができる(作成はPC想定でも可)
- ✅ 自分が実際の仕事で1ヶ月使い続けられる

## 2. データモデルの骨格(先に決めるべき部分)

前回指摘した「書類間の連携ロジックが未設計」への対応として、最低限のエンティティ関係を先に決めます。

```
顧客(Customer)
  └─ 案件(Project) ※進捗管理の単位
        └─ 見積書(Quote)
              └─ 契約書(Contract) ← 見積の項目を継承
                    ├─ 計画書(Plan)
                    │     ├─ 受注表(OrderSheet)
                    │     └─ タスク管理表(TaskList)
                    └─ 覚書(Memo)
              └─ 請求書(Invoice) ← 契約の内容を根拠に生成 [1契約:N請求書]
                    └─ 領収書(Receipt)

組織(Organization) ※将来のマルチテナント対応
  └─ ユーザー(User) ← 権限(Owner / Member / Viewer 等)
        └─ 顧客(Customer)以下すべてが Organization に紐づく
```

**設計上のポイント**
- 見積→契約→請求は「複製して編集」ではなく「参照して差分のみ持つ」構造にしないと、見積を直したときに契約に反映されない問題が起きます。実装時はステータス遷移(見積中→契約済→請求済)を明示的に持たせるのが安全です。
- 確定申告・事業用口座は上記の外側(会計データのエクスポート層)として別モジュール化し、コアのドキュメントフローとは疎結合にすることを推奨します。
- **請求書は1契約に対して複数作成可能(1:N)で確定。** 分割請求・月次請求に対応するため、Invoiceは必ずContractへの外部キーを持ち、「この契約に対して何回目の請求か」を管理するフィールド(請求回次・請求済み金額の合計等)を持たせる必要があります。合計請求額が契約金額を超えないようにするバリデーションも忘れずに。
- **Organization(組織)エンティティを最初から入れることが確定。** 「自分専用ツールとして作って後から複数ユーザー対応にする」というやり方は、全テーブルに`organization_id`を後付けする大改修になりがちです。MVPの時点でユーザーが1人(本人)であっても、テーブル設計上は「組織に紐づく」形にしておきます。ただし招待機能や課金など複雑な権限UIはPhase 3以降でよく、Phase 0では「組織=本人+テスター」の固定運用で十分です。

## 3. フェーズ分割案(MVP → 拡張)

| フェーズ | スコープ | 目安 |
|---|---|---|
| **Phase 0(MVP)** | 顧客管理 / 見積書・契約書・請求書の作成・PDF出力・一覧管理 / 案件単位の進捗ステータス管理 | 最初の到達点 |
| **Phase 1** | 計画書・覚書・受注表・タスク管理表(契約書の子要素) / 領収書管理 | MVP運用後、実際の業務で足りないと感じた順に |
| **Phase 2** | ダッシュボードのカスタマイズ機構 / 機能の追加拡張(プラグイン的な仕組み) | コア機能が固まってから。ここを先に作ると土台変更のたびに作り直しになる |
| **Phase 3** | 確定申告データ連携 / 事業用口座連携 / モバイルネイティブアプリ / プラグイン機構 | 外部サービス連携の検討を含む。ビルド vs バイ(freee/MoneyForward連携)の判断が必要 |

**この順序で確定。** ただしPhase 0の設計時点でOrganization/権限モデルだけは入れておく(セクション2参照)。

## 4. 技術スタック(確定: TypeScript統一)

| 領域 | 確定 | 理由 |
|---|---|---|
| フロントエンド | Next.js (TypeScript) | Web+将来のPWA化を見据えるとNext.js単体で完結できる |
| バックエンド | Next.js API Routes(または将来分離を見据えTRPC/Route Handlers) | フロントと同一言語・同一リポジトリで開発速度を優先。書類PDF生成が重くなればワーカー分離を検討 |
| DB | PostgreSQL + Prisma | 書類間の関係性が強く、Organization/権限モデルもリレーショナルの方が扱いやすい |
| PDF生成 | React-PDFまたはPuppeteer(HTML→PDF) | 日本の商習慣に沿った帳票レイアウトの自由度で選定。要検証 |
| 認証・権限 | NextAuth(Auth.js) + Organization単位のRBAC(Owner/Member/Viewer) | 将来の他人への提供・販売を見据え、MVPの段階からOrganization/ロールの概念だけは入れる |
| ホスティング | Vercel(フロント/API) + Supabase または Neon(Postgres) | 個人開発〜小規模販売まで運用コストを抑えられる構成 |

**この技術スタックで確定。** 実装フェーズではこの構成をベースに、Claude Codeで`package.json`初期構成から着手します。

## 5. 想定される失敗パターン(着手前に予測)

1. 見積→契約→請求のデータ継承を後付けで作ろうとして、書類同士が独立管理になり転記地獄が再発する
2. 拡張機構を先に作ってしまい、コア機能の仕様変更のたびに壊れる
3. PDF帳票のレイアウト調整に想定以上の工数がかかる(日本の商習慣特有の書式要求が多い)
4. 確定申告・口座連携を自作しようとして法令調査に時間を溶かす
5. モバイル対応を最初から求めて、PC版の作り込みが遅れる
6. ダッシュボードのカスタム機構が複雑になりすぎてMVPの完成が遠のく
7. 顧客管理(CRM)の項目設計が甘く、後から必須項目を追加すると既存データの移行が必要になる
8. Fable 5.1レビューを毎コミットで回してしまい、設計が固まる前にレビューコストだけがかさむ
9. 契約書・見積書・請求書のステータス遷移(下書き→送付済→承認済等)を後回しにして、業務フローと画面が噛み合わなくなる
10. 1人開発でPM役も自分が兼任するため、要件のブレをチェックする第三者視点が不足しがちになる(→ Fable 5.1を設計レビューに使うのはここで効いてくる)
11. 「Phase 0では組織=本人+テスター固定」のつもりが、テスターの声を受けて早期に招待・権限UIまで作り込んでしまい、Phase 0のスコープが膨らむ
12. 分割請求(1契約:N請求書)のバリデーション(請求済み合計が契約金額を超えない等)を後回しにして、テスト運用中に金額の不整合が発生する

## 6. PM + サブエージェント運用計画(Claude Code想定)

`claude-model-operation-guide.md` の役割分担をベースに、開発フェーズごとに適用します。

| フェーズ | PM(統括) | 実装 | 査読 |
|---|---|---|---|
| 設計(データモデル・アーキテクチャ) | 本人 or Opus 5 | - | **Fable 5.1(medium effort)** ← 最もコスパが高い工程 |
| Phase 0 実装 | Opus 5 | Opus 5(主要機能) / Sonnet 5(ボイラープレート・テスト生成) | 機能単位の区切りごとにFable 5.1へ設計レビューのみ依頼(コードレビューは構造安定後) |
| Phase 1以降 | Opus 5 | Opus 5 / Sonnet 5 | PRごとにFable 5.1コードレビュー(深刻度×確信度でランク付け、件数上限あり) |
| 原因不明のバグ・障害 | - | - | Fable 5.1(effortを上げて投入) |

**運用ルール(ガイド準拠)**
- 査読役(Fable 5.1)にパッチを直接当てさせない。指摘→承認ゲート→実装側が適用。
- リポジトリ全体を渡さず、差分+依存ファイルに絞る。
- 常時参照する設計ドキュメント(このファイル含む)はキャッシュ対象として固定する。
