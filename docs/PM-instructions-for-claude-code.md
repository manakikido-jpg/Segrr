# Claude Code 引き継ぎ用 PM指示書

このドキュメントはClaude Code側のPM(統括)役に向けた指示です。着手前に以下を読み込んでください。

## 読む順番

1. `docs/segrr-requirements-v1.md` — 要件定義書(このプロジェクトの正)
2. `docs/project-structure.md` — ファイル構成
3. `docs/phase0-task-breakdown.md` — タスク分解(依存関係・工数付き)
4. `claude-model-operation-guide.md` — モデル運用方針(役割分担のルール)

## 進め方

`phase0-task-breakdown.md`のトラックA(基盤系)から着手すること。A1完了後はA2/A3/A4を並行セッションで進められる。A2完了後はトラックB(業務系)を直線的に進め、B6完了後にトラックC(収束タスク)へ進む。

各タスクについて:

1. **着手前**: タスクの設計方針(データの流れ・画面構成)を短くまとめ、**Fable 5.1(medium effort)** に設計レビューを依頼する。指摘は採否を自分(PM)で判断してから実装に進む。
2. **実装**: ボイラープレート・単純なCRUD・テストコード生成は**Sonnet 5**、ビジネスロジック(見積→契約→請求の変換処理、金額バリデーション等)は**Opus 5**が担当する。
3. **完了後**: タスク表の「完了条件」を満たしているか確認する。タスク6〜8(見積・契約・請求)は工数が大きいため、完了条件を満たした時点で**Fable 5.1にコードレビューを依頼**(差分+依存ファイルのみ渡す。リポジトリ全体は渡さない)。指摘は深刻度×確信度でランク付けし、上位のみ採用する。
4. 査読役(Fable 5.1)には**パッチを直接当てさせない**。指摘→人間またはPMの承認→実装側モデルが適用、の順を必ず守る。

## 特に注意してほしい箇所(要件定義書の失敗パターンより抜粋)

- タスクB6(請求書): 分割請求の合計金額が契約金額を超えないバリデーションは、UI・`server/services/invoice-service.ts`(サービス層)・DBトリガー(`docs/db-constraints.sql`)の三重で守ること。UIバリデーションのみだとAPI直叩きで不整合が起きる。
- タスクB1(認証・Organization): 「後で複数ユーザー対応する」という妥協をしないこと。Phase 0の時点でOrganizationに紐づかないテーブルを作らない。
- 見積→契約、契約→請求の変換処理は、明細を複製(コピー)する実装にすること。参照だけで済ませると、元の見積・契約を後から編集した際に確定済みの契約・請求の金額が変わってしまう。
- タスクC1(案件詳細画面): この会話中に作成したワイヤーフレーム(タイムライン形式、書類ごとに次アクションボタン)を実装の参考にすること。UI設計を一から考え直さない。

## 完了時の報告フォーマット

各タスク完了時、以下を人間に報告すること:

```
タスク#: [番号] [タスク名]
完了条件: 満たした / 一部未達(理由)
Fable 5.1レビュー: 実施した(指摘N件、採用N件) / 未実施(理由)
次のタスクへの申し送り事項: あれば記載
```

## モデル切り替えの実務(補足)

`.claude/commands/` にモデル指定込みのコマンドを用意しておくと、毎回指定する手間が省ける。例:

- `/review-design` → Fable 5.1・medium effortで設計レビューを依頼するコマンド
- `/review-code` → 差分ファイルを渡してFable 5.1コードレビューを依頼するコマンド
- `/implement` → Opus 5でビジネスロジックを実装するコマンド

これらのコマンド化自体はタスク1(初期セットアップ)の一部として着手して構わない。
