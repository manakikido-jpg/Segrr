# ADR-001: 帳票PDFの生成方式

決定日: 2026-09-17 / タスク: A4 / 状態: 採用

## 背景

要件定義書セクション4は「React-PDF または Puppeteer(HTML→PDF)。日本の商習慣に沿った
帳票レイアウトの自由度で選定。要検証」としていた。セクション5の失敗パターン3
「PDF帳票のレイアウト調整に想定以上の工数がかかる」が最大のリスク。

## 検証したこと

両方式を実際に動かして比較した。

| | @react-pdf/renderer | HTML → headless Chromium |
|---|---|---|
| 動作 | **4.9.0 は依存の `@react-pdf/hyphenate` の exports マップが壊れており Node から読めなかった** | 実測1書類あたり約1秒で生成できた |
| 罫線の多い表 | flexbox の部分実装。罫線・改ページ・ヘッダー再掲を手で組む | CSS の `table` がそのまま使える。`display:table-header-group` でヘッダー再掲、`break-inside:avoid` で行の分断防止 |
| 日本語 | 可変フォント不可。静的ウェイトの TTF/OTF が必要 | OTF をそのまま埋め込める |
| デザイントークン | 使えない(独自のスタイル記法) | `src/styles/tokens.css` と同じ値をそのまま使える |
| デプロイ | 純JSで軽い | Chromium が必要 |

**検証中に見つけた重要な落とし穴**: フォントを指定しないと Chromium は別のCJKフォントへ
フォールバックする。実測では `WenQuanYiZenHei`(中国語フォント)が選ばれ、
日本語として誤った字形で印字された。サーバーによっては日本語フォントが一切なく豆腐になる。
→ Noto Sans JP を同梱し、`@font-face` で明示的に埋め込む(`src/assets/fonts/`)。

## 決定

**HTML → headless Chromium (playwright-core) を採用する。**

失敗パターン3のリスクを最小化することを最優先した。日本の帳票は罫線の多い表が中心で、
CSS の table がそのまま使える差は大きい。画面側のデザイントークンを共有できることで、
UIと帳票の見た目がずれる問題も避けられる。

## 引き換えに受け入れるコスト

デプロイ先に Chromium が必要になる。Vercel に載せる場合は次のいずれか:

1. `@sparticuz/chromium` を使う(関数サイズとコールドスタートが増える)
2. PDF生成だけ別ワーカーに分離する(要件定義書セクション4が想定している構成)

Phase 0 は本人+テスターの運用なので判断を先送りできる。実行ファイルのパスは
`CHROMIUM_EXECUTABLE_PATH` で差し替えられるようにしてあり、方式変更時の影響は
`src/lib/pdf/render.ts` に閉じている(レイアウトは `template.ts` 側で変わらない)。

## 設計上の約束

- **3書類で1つのレイアウト**(`src/lib/pdf/template.ts`)。見積・契約・請求の差分は
  表題・日付ラベル・源泉徴収・請求回次だけなので、書類ごとに複製しない。
  複製すると登録番号の印字位置や敬称を直すたびに3箇所を触ることになる。
- **Prisma の型に依存しない**(`src/lib/pdf/types.ts`)。3書類で別モデルのため。
- **金額はここで計算しない。** DBが算出した値を受け取って印字するだけ。
- 適格請求書の要件(発行者名・登録番号・取引年月日・取引内容・税率ごとに区分した
  対価の額と適用税率・税率ごとの消費税額・交付先の名称)を満たす。
  登録番号が未設定(免税事業者)なら欄ごと出さない。
